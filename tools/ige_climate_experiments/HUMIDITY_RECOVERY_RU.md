# Продолжение после Auxiliary p: UNRESOLVED_OPTIMIZATION

Версия дополнения — 0.2.1. Требуется существующая папка программы с ядром 0.1.2 и ранее установленным дополнением влажности 0.2.0.

## Что произошло

В пользовательском запуске `20261108T191838_341211Z_5ea72a0b` завершены общие T/p на D и два внутренних блока. При подготовке последнего блока из 31 площадки не завершилась численная оптимизация вспомогательного давления. Это произошло до обучения 18 кандидатов влажности и до их сравнения на V. C не открывалась.

Архив содержит целый численный куб и проверяемые контрольные точки. E0 показывает ноль неразрешённых ошибок. Версия 0.2.0 не сохранила трассу **неудачной** оптимизации, поэтому нельзя установить по архиву, был ли причиной лимит оценок, итераций, времени или численный сбой поиска. В Linux на присланных данных с исходными параметрами этот же блок сошёлся. Среды отличаются: исходная Windows — Python 3.12.10 / NumPy 2.5.4 / SciPy 1.18.1; локальная проверка — Python 3.12.14 / NumPy 2.3.5 / SciPy 1.17.0. Это согласуется с зависимостью численного поиска от среды, но не доказывает дефект какой-либо библиотеки.

## Что сделать

1. Распакуйте `IGE_Humidity_Recovery_v0_2_1.zip` прямо в существующую `IGE_Automatic_Regression_v0_1_0`, рядом с `ige_humidity.py`, с заменой файлов программы из архива.
2. Запустите **`RUN_HUMIDITY_RECOVERY.bat`**. Для указанного выше запуска путь уже задан. `config_auto_regression.json` и пути Database менять не нужно.

Эквивалент:

```bat
.venv_regression\Scripts\python.exe ige_humidity.py recover --run "humidity_results\20261108T191838_341211Z_5ea72a0b"
```

BAT также принимает путь к другому совместимому исходному запуску первым аргументом. На C-открытый запуск или на запуск с уже выполненным подбором влажности на V данное продолжение не распространяется. Для перенесённого исходного файла когорты CLI имеет `--anchor`: содержимое и контрольная сумма должны совпасть с исходными. Этот параметр меняет только местоположение файла, не распределение станций или лет.

Будет создан **новый дочерний каталог** в `humidity_results`. Программа выведет его путь. Численный куб копируется и проверяется без изменения значений; E0 и загрузки повторно не выполняются. В данной ситуации переносятся три завершённых блока: `aux_full_D`, `aux_inner_0`, `aux_inner_1`, то есть шесть моделей T/p. Проверяются их хеши, принадлежность исходному запуску, семейства и годы обучения. Последний неполный блок пересчитывается. Для незнакомой реализации или повреждённой контрольной точки программа остановится.

Обычный `resume` старого каталога после изменения программы использовать не следует: защита замороженного кода правильно отвергнет его. `recover` создаёт новую спецификацию, записывает происхождение перенесённых точек и сохраняет исходную спецификацию без подмены хешей. Уже успешные старые модели не выдаются за заново пересчитанные.

Если **новый дочерний** расчёт прервётся, продолжайте именно его:

```bat
.venv_regression\Scripts\python.exe ige_humidity.py resume --run "humidity_results\НОВЫЙ_КАТАЛОГ"
```

Повторный `recover` исходного каталога создаёт ещё один дочерний запуск. Поэтому после создания дочернего каталога для возобновления используйте `resume`, а не повторный двойной щелчок recovery BAT.

## Изменение численного алгоритма

Исходная L-BFGS-B выполняется с прежними настройками. Только при незавершении поиска добавляются две зарегистрированные попытки на **той же внутренней выборке D** и с **той же функцией и границами**:

1. L-BFGS-B с абсолютным шагом численной производной 1e-5 и расширенным бюджетом.
2. Если он тоже не сошёлся — ограниченный непрерывный метод Powell без численной производной.

На дополнительный метод отводится до 900 оценок, 180 итераций и 600 s, с проверками времени между оценками. Коэффициенты по-прежнему решаются регрессией; резервный поиск меняет непрерывные параметры пространственных весов. Ни станции, ни часы для облегчения сходимости не исключаются. Неудачная оптимизация не объявляется успешной. При невозможности найти допустимую сходимость сохраняется причина остановки.

Этот резерв действует как для T/p, так и для кандидатов влажности, с сохранением их собственной исходной функции потерь. Успешно сошедшиеся исходные попытки не пересматриваются. Политика резервного поиска зафиксирована в `run_spec.sealed.json` до подбора по V. Данных V/C в резервном поиске нет. Достижение границы параметра не перестаёт быть диагностическим ограничением модели.

Справочная документация API: [L-BFGS-B](https://docs.scipy.org/doc/scipy/reference/optimize.minimize-lbfgsb.html), [Powell](https://docs.scipy.org/doc/scipy/reference/optimize.minimize-powell.html). Это обоснование использования численных методов, а не доказательство преимущества интерполяции.

## Что сохраняется

`recovery_lineage.json` связывает новый запуск с исходным ID и хешами; `checkpoints/` отмечает происхождение каждого перенесённого блока. `diagnostics/aux_*/T_optimization.json` и `p_optimization.json` теперь сохраняются **до** возможного исключения, включая неудачные попытки. Модели влажности сохраняют свою полную трассу в `models/`.

Результаты сравнения — `summary.json`, `chain_comparison.csv` и `REPORT_RU.md` в новом дочернем каталоге. Исходный каталог и Database сохраняются. C автоматически не открывается. Само продолжение и успешный код завершения не являются доказательством научного преимущества модели или допуска EPW.
