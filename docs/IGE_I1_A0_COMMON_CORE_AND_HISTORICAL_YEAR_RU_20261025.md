# IGE: общее ядро I1 и полный исторический год A0

Дата: 25 октября 2026. Родитель: `5481a74dabb9acf40dd745d0006d0a9bc1cea4aa`.
Ветка: `research/ige-i1-a0-common-core-20261025`.

Первый исполняемый маршрут нового ядра: координаты + исторический год → оригинальные ответы провайдеров → почасовой ряд → EPW → отчёт и журнал. Собран **Graz 2023, 8760 × 35**. Это фоновый исследовательский год для выбранной ячейки; функция точной локальной реконструкции по станциям остаётся этапом A1.

## Что реализовано

Код расположен в `tools/climate_analyzer/epw_climate_analyzer/engine/` и использует существующую `CanonicalClimateDataset`. Прежние загрузчики EPW, UI и исследовательские алгоритмы не переписаны.

| Компонент | Назначение и фактический объём |
| --- | --- |
| `HistoricalRequest` | Координаты, реальный год, фиксированный стандартный UTC offset, явно ограниченный режим `grid_background`; отдельно заданная высота с источником/datum |
| `FutureRequest` | Контракт идентичности базы SHA, GCM/member/SSP, исторического и будущего окна, версии определений и отдельного года исторического рисунка. Генератор будущего здесь ещё не реализован |
| `ClimateResult` | Почасовой ряд, определения и временные операторы каждого поля, источники, преобразования, корректировки и четыре отдельных статуса качества |
| `run_historical` | Один вызываемый путь для получения или воспроизведения исходных данных, сборки года и записи результатов |
| Экспортёр EPW | Параметрические координаты/год/стандартный час, 8760 или 8784 строк, сохранение 29 февраля, независимое чтение CSV после записи |
| Адаптер Analyzer | Прямой переход в canonical dataset с `calendar_mode=historical` и датами 2023; привычная загрузка пользовательского EPW по-прежнему имеет типичный календарь |
| Журнал | Исходные байты и SHA, происхождение полей, изменения единиц/временной адресации, отдельная квантизация облачности при экспорте, отсутствие скрытого заполнения |

Текущий маршрут поддерживает полные годы 2002–2025 при доступности и прохождении QC обоих провайдеров. Это ограничение политики источников, а не заявление о проверенной точности всех точек/лет. Реально испытан исходный год Graz 2023; другие координаты и високосные/отрицательные часовые зоны проверены синтетическими контрактными примерами. В версии v1 разрешены целочасовые стандартные зоны от UTC−12 до UTC+12. Дробный offset блокируется с явным сообщением о необходимости временного переразбиения; округления нет. DST не используется.

Высота пользователя в контракте не запускает автоматическую поправку: в A0 она сохраняется как запрос, отдельно от непроверенной высоты фоновой ячейки. `local_reconstruction` блокируется, пока A1 не реализован.

## Источники и геометрия

| Поля | Источник | Обработка |
| --- | --- | --- |
| T, Td, RH, абсолютное p, ветер, total cloud | Open-Meteo, явный `models=era5`, `elevation=nan`, `cell_selection=nearest` | ERA5-derived продукт провайдера, не аутентифицированный исходный CDS GRIB; статистическое высотное downscaling отключено |
| GHI, direct horizontal, DHI, DNI | Тот же ответ Open-Meteo | Сохраняются часовые потоки провайдера; собственная декомпозиция солнечной радиации не добавлена |
| Liquid rain и total precipitation | Тот же ответ, отдельные `rain` и `precipitation` | В EPW попадает liquid rain; total precipitation сохранена в почасовой таблице и сводке |
| L↓ | NASA POWER hourly, `ALLSKY_SFC_LW_DWN`, UTC | Оригинальные значения; ответ сообщает `SYN1DEG`. Иная пространственная и радиационная цепочка явно сохранена |

Для запроса **47.0707° N, 15.4395° E** провайдер выбрал **47.0° N, 15.5° E**, расстояние **9.1008 км**. EPW LOCATION содержит координаты фоновой ячейки. Координаты запроса остаются в manifest; нельзя выдать этот файл за скорректированный климат самого участка.

Поле высоты Open-Meteo равно **467 м**. Оно помечено как **непроверенный proxy**, а не подтверждённая нативная орография ERA5 или высота участка/датчика. Именно этот явно отмеченный proxy используется в заголовке EPW. Давление остаётся на модельной поверхности. Высоты датчиков Graz Universität из прежних экспериментов к этим данным не подставляются.

POWER сообщает геометрию point около запрошенных координат; это не доказательство совпадения его атмосферного столба с ERA5. Историческая совместная точность longwave, облачности, влажности и радиации не квалифицирована. Поверхностные потоки SYN1deg являются продуктом радиационного расчёта, а не локальными наземными наблюдениями.

## Время и уравнения преобразований

Пусть $s_i$ — начало часа в фиксированном местном стандартном времени, $o$ — offset, $u_i=s_i-o$ — начало UTC-интервала. Каноническая строка относится к $[u_i,u_i+1\,h)$.

Для мгновенных полей Open-Meteo и состояния EPW применяется конец интервала:

$$X_i=X^{OM}(u_i+1\,h).$$

Для Open-Meteo радиация — среднее за предшествующий час; дождь — сумма за тот же час. POWER маркирует среднее началом часа. Поэтому:

$$E_i^{SW}=F^{OM}(u_i+1\,h)\,\Delta t,\qquad E_i^{LW}=F^{POWER}(u_i)\,\Delta t,\qquad\Delta t=1\,h.$$

При $F$ в W/m² результат $E$ имеет единицы Wh/m². Равенство чисел возникает только из-за длительности 1 час, а не взаимозаменяемости величин.

Для Graz UTC+1 первая строка EPW `2023,1,1,1,60` описывает местный час 00–01. Его UTC-начало — **2022-12-31 23:00**, UTC-конец — **2023-01-01 00:00**. Open-Meteo берётся по конечной метке, POWER по начальной. Последняя строка — `2023,12,31,24,60`. Ранее фиксированные CET/start-label допущения старого экспортёра сюда не перенесены. Старые результаты сохранены.

Давление преобразуется как

$$p_{Pa}=100\,p_{hPa}.$$

Выбирается **surface_pressure**, а не pressure_msl: абсолютное давление у модельной поверхности, без обратного пересчёта приведённого давления. Семантика DWD, исправленная P9.3B2D, не нарушается; DWD вообще не участвует в A0. Перенос p на уровень T/RH 2 м здесь не заявляется и не выполняется по непроверенной высоте.

Контракт различает q и суховоздушное влагосодержание приложения:

$$w_{g/kg\,dry}=1000\frac{q_{kg/kg\,moist}}{1-q_{kg/kg\,moist}}.$$

Этот переход проверен отдельно. Сам A0 **не генерирует q** из неоговорённого сочетания RH и поверхностного давления и не выдаёт его за исходный NASA huss.

## Проверки влажности и физических пределов

T, Td и RH сохраняются в точности, в которой их передаёт Open-Meteo. Определение RH у провайдера — Magnus над жидкой водой:

$$R(T,T_d)=100\exp\left(\frac{17.625T_d}{243.04+T_d}-\frac{17.625T}{243.04+T}\right).$$

T/Td выдаются с шагом 0.1 °C, RH — 1 процентный пункт. Проверяется наличие общего состояния в интервалах округления, а не подобранный порог MAE. При $a=0.05\,K$, $b=0.5$ процентного пункта:

$$[R(T+a,T_d-a),R(T-a,T_d+a)]\cap[RH-b,RH+b]\cap[0,100]\ne\varnothing.$$

В численных границах добавлено $10^{-6}$ на представление десятичных границ. Все **8760** часов совместимы с этим условием. Максимальная разность между формулой на округлённых T/Td и исходным целым RH — **1.120922 процентного пункта**. Это объясняет округлённую совместимость; не доказывает точного почасового T–p–q–RH closure и не характеризует ошибку относительно станций.

Адаптер сохраняет определение RH и **не вычисляет** ASHRAE water/ice humidity ratio приложения автоматически. Прямое использование такого RH в старом ice-branch расчёте ниже нуля без фазового адаптера было бы ошибкой. До U1 этот маршрут не подключён к UI. B-M1 должен явно разрешить фазовую семантику, p-proxy и способ получения q; NASA NEX tas midrange, huss/hurs и их суточные операторы не заменяются определениями NASA POWER или Open-Meteo.

Дополнительно проверяются конечность/полнота, допустимые диапазоны T/Td/RH/p/ветра/радиации/дождя, Td≤T с учётом выходной точности, DHI≤GHI, liquid rain≤total precipitation и горизонтальная сумма GHI=direct horizontal+DHI. Здесь её максимальная невязка **0 Wh/m²**. Равенство DNI×cos(зенит в середине часа)+DHI не навязывается часовым средним как точное тождество.

Непредоставленные opaque sky, illuminance, visibility и другие вспомогательные EPW поля имеют штатные missing-коды. Они не заменены нулями. Общее облачное покрытие при EPW экспорте округляется до целых десятых: максимум изменения 0.5 tenths; правило отдельно отражено в ledger. Период измерения rain равен **1 часу**, в том числе в сухие часы; это не длительность фактического дождя.

## Повторение

Из корня репозитория, на Python 3.12 с NumPy 1.26.4 / pandas 2.3.3:

```bash
python research/ige_cmip6/i1_a0_verify.py --out outputs/i1_a0_verified
```

Команда проверяет контракты и старые компоненты, сохраняет отдельный receipt, затем собирает год из оригинальных зафиксированных ответов. Сеть для проверки запрещена на уровне socket.connect. Для **каждого из 8760 часов** дополнительно проверяются адреса исходных T/p/rain/GHI/LW в JSON, независимо от проверки writer/readback.

Для новой исходной загрузки:

```bash
PYTHONPATH=tools/climate_analyzer python -m epw_climate_analyzer.engine historical \
  --latitude 47.0707 --longitude 15.4395 --year 2023 \
  --utc-offset-minutes 60 --label Graz --out outputs/graz_2023_new_acquisition
```

Для отдельного повторения без сети добавляются:

```bash
  --source-bundle research/ige_cmip6/i1_a0_graz2023_original_sources_20261025.zip \
  --source-bundle-sha256 2575be295bc41be68ac56940524a76c5ef9f9b5010a83f20b6eec21c49dce273
```

Выходная папка обязана быть новой. Изменение источников, единиц, временных меток, POWER source chain, неполнота, ошибка контрольной суммы или физического экрана блокируют полный результат. Повторная загрузка с изменившимися служебными полями не перезаписывает предыдущий пакет; новая acquisition имеет собственные SHA. При ошибке сохраняется `failed.json`; только успешный `manifest.json` означает завершённую сборку.

Пакет полного года содержит `climate.epw`, `hourly.csv.gz`, `monthly_summary.json`, `manifest.json`, `ledger.json`, `sources.zip`. В нём фиксируются контрольные суммы исходников и модулей реализации.

## Первичные определения

- [Open-Meteo historical API](https://open-meteo.com/en/docs/historical-weather-api): фиксированный ERA5, единицы, мгновенные поля, предшествующие часовые потоки и суммы, `elevation=nan`.
- [Исходный код Open-Meteo Meteorology](https://github.com/open-meteo/open-meteo/blob/main/Sources/App/Helper/Meteorology.swift): Magnus relativeHumidity/dewpoint, 17.625/243.04. Это определение провайдера, не NASA NEX RH-phase policy.
- [NASA POWER hourly API](https://power.larc.nasa.gov/docs/services/api/temporal/hourly/): средние по часам, временные стандарты.
- [NASA POWER Other FAQ](https://power.larc.nasa.gov/docs/faqs/other/): UTC/LST и метка начала часа.
- [CERES SYN1deg](https://ceres.larc.nasa.gov/Data/): радиационные поверхностные потоки, пространственная/физическая природа продукта.
- [EnergyPlus 24.1 Auxiliary Programs](https://energyplus.net/assets/nrel_custom/pdfs/pdfs_v24.1.0/AuxiliaryPrograms.pdf): EPW, hour-ending состояния и предшествующие интервалы радиации.
