## 3. Реальные разрывы интеграции

| Блокер | Для какой функции | Почему обязателен до соответствующего рабочего режима |
|---|---|---|
| Нет единого service/CLI и request/result контракта | A, B | Нельзя повторяемо вызвать всю цепь по пользовательскому запросу |
| Разные словари, единицы, временная поддержка, высоты | A, B | q не равно mixing ratio; instantaneous T нельзя незаметно назвать часовым средним; p должен иметь объявленную высоту |
| Жёсткие Graz/2013/CanESM5/CET и 8760 в ранних entry points | A, B | Экспортёр не является универсальным только потому, что умеет записать один год |
| UTC → фиксированное местное стандартное время, граничные часы, leap policy | A, B | Без них ряд может сдвинуться или потерять часы. DST не включается. Дробные timezone offsets нельзя молча округлять |
| Фоновый P9.1A имеет 12 полей, но не L↓ | A → B | Старый morphing reader требует longwave. Нельзя выдать неполную историческую базу за полноценный вход B или заполнить LW нулём |
| Неподтверждённая provider elevation | A | `elevation` из ответа Open-Meteo не удостоверяет высоту исходной ERA5-ячейки. Запрещена автоматическая неподтверждённая высотная поправка |
| Наблюдения, сетка и локальная реконструкция смешиваются в статусах | A | Чтение станции не доказывает интерполяцию произвольной точки; grid-прототип не закрывает локальную A |
| Legacy tas используется как изменение почасового среднего | B-M | Архивированный NEX-контракт фиксирует `tas=(tasmin+tasmax)/2`, а не time mean. Для нового маршрута нужен согласованный температурный estimand |
| Clipping q при насыщении | B-M | Теряется заявленный сигнал huss. Уже существующая месячная проекция — кандидат для первого маршрута; нужны feasibility check и журнал, а не неучтённое clipping |
| Нет общей схемы качества полей/допусков | A, B | Нельзя назвать unknown cloud/illuminance нулевыми данными или разрешить расчёт, которому этих данных не хватает |
| В интерфейсе нет вызова генератора | A, B | Сейчас источники — Upload EPW / Find climate / GeoSphere Austria. Нужна связь request → job → canonical result → download |

Привязка к исходным модулям хранится в `module_inventory` результата аудита. Существующая `CanonicalClimateDataset` уже даёт основу адаптера приложения; не требуется создавать второй независимый DataFrame-стандарт.

## 4. Единые интерфейсы

**HistoricalRequest:** WGS84, период, режим `grid_background` / `local_reconstruction`, высота и datum/источник, политика источников/станций и QC, календарь и export clock. **FutureRequest:** ID/SHA исторической базы, GCM/member/SSP, историческое и будущее окна модели, метод `monthly_morph` / `daily_joint`, source semantics version и seed там, где он действительно нужен.

**ClimateResult:** канонический почасовой dataset, исходные и расчётные временные интервалы, requested/source coordinates, grid/site height и p-reference, единицы и происхождение каждой величины, QC/missing mask, журнал преобразований и поправок, run manifest и SHA, отдельные readiness/capability flags, EPW + машиночитаемый отчёт. Наличие одного EPW не удаляет эти метаданные.

Внутри расчёта p — Pa, q — kg/kg **влажного воздуха**, T — K либо явно помеченные °C на границе. Если приложению нужен humidity ratio w в g/kg **сухого воздуха**, используется $w=1000q/(1-q)$; прямое переименование q недопустимо. Для потоков сохраняются interval start/end и $H=\bar F\Delta t$: W/m² и Wh/m² совпадают численно только при Δt=1 h.

Исторический результат активируется как `calendar_mode=historical` с реальными датами, не через неявный EPW-typical-year импорт. Будущий представительный год хранит исходный pattern year отдельно от GCM climate window; он не объявляется реальной хронологией 2050 года и не является автоматически TMY.

## 6. Минимальная математика B-M1 и место C2

Требуемый минимум — согласованное определение величин, а не общий нелинейный оптимизатор на каждые сутки. Предлагаемый температурный контракт нового B-M1:

$$c_d=\tfrac12(T_{\min,d}+T_{\max,d}),\qquad T'_h=c_d+\delta_d+\beta_m(T_h-c_d).$$

Здесь $\delta_d$ строится по изменениям распределения **того же midrange-index**, $\beta_m$ — отношение средних модельных DTR. Центрирование $\delta_d$ сохраняет месячный сдвиг среднего **индекса c**, не выдавая его за сдвиг time-mean T. При $\beta_m>0$ выходной midrange равен $c_d+\delta_d$, DTR масштабируется на $\beta_m$. Это **план адаптации**, а не уже выполненный расчёт: текущий replay намеренно использовал неизменённый legacy алгоритм. Истинные субчасовые экстремумы GCM и экстремумы доступных hourly reference nodes дополнительно различаются.

Для влажности сохраняется уже существующая простая месячная постановка:

$$q_h^*=r_{q,m}q_h^{base},\qquad \min_q \tfrac12\sum_h(q_h-q_h^*)^2,$$
$$q_{lo,h}\le q_h\le q_{hi,h},\qquad \sum_{h\in m}q_h=\sum_{h\in m}q_h^*.$$

Это выпуклая box+sum проекция с решением $q_h=\operatorname{clip}(q_h^*+\lambda_m,q_{lo,h},q_{hi,h})$. При допустимом месячном target не требуется C2 multistart. Нижняя граница RH=1% в legacy — **модельная политика, не универсальный физический закон**; в новом контракте её нужно определить явно. При недопустимом target — зарегистрированный отказ/отдельная явная политика, без скрытого изменения массы.

После этого $e=pq/[\epsilon+(1-\epsilon)q]$, $RH=100e/e_s(T)$ и Td восстанавливаются согласованно. EPW RH/dewpoint phase и NEX hurs WATER_ICE — разные объявленные операторы; B-M1 не обязан точно воспроизводить native daily hurs, и не должен обещать это. Временные bounds NASA остаются открытым вопросом B-D/source admission, а не заменяются неявным «средним из 24 часов».

Для первого B-M1 допустимо явно объявленное $p'_h=p_h^{base}$ как условный pressure proxy; это не восстановленный будущий ps GCM. GHI/осадки/ветер/LW получают отдельные объявленные месячные сигналы и проверки; направления ветра, мокрые часы и часть облачной хронологии наследуются. База и missing fields сохраняются с происхождением, а не становятся будущими наблюдениями.

**C2 нужен B-D**, когда хотим совместно удовлетворять суточным ограничениям и воспроизводимо разрешать их несовместимость. Его программные/производные тесты, физическая допустимость и локальный F не доказывают лучшую независимую часовую точность. Замена более простого основного метода — только после отдельного доказательного сравнения.

## 7. Что обязательно, что можно развивать отдельно

До исследовательского сквозного прототипа обязательны: подлинные полные входы, единицы/операторы/высоты, календарь, физические проверки, честный missing handling, сохранение **объявленного** климатического сигнала, воспроизводимые файлы и понятный статус в интерфейсе. Отсутствие критичного для выбранного режима поля — блокер, а не «ограничение точности».

До квалифицированного использования обязательны независимые показатели в заявленной области и настоящий EnergyPlus smoke/сравнение на **самих** итоговых файлах. Успешный EnergyPlus не доказывает климатическую точность. Для daylighting нужны независимо обоснованные radiation/photometry inputs; незаполненные illuminance/opaque sky не становятся нулевыми.

Развиваются отдельно: универсальная модель инверсий, дорогостоящие native-column эксперименты, новые семейства оптимизаторов, независимый прогноз будущего направления ветра/облачной и осадочной хронологии, мировой станционный benchmark. Их отсутствие не блокирует честно ограниченный B-M1, но соответствующие возможности не заявляются.

Прежний обязательный readback 28 лицензированных Meteonorm-основанных файлов относится к **тому** исследовательскому маршруту. Он не становится условием существования нового прототипа на открытой базе A. Новая база всё равно проходит собственные проверки; старые отрицательные результаты и gate-записи не переписываются.
